## ขอบเขต

- File Browser เชื่อม upload, download, rename, move และ copy ผ่าน Nexora same-origin `/api/storage/v1/*` endpoints ที่มีอยู่แล้ว.
- ทุก operation ตรวจ capability และ mount/capability read-only state ใน UI; server ตรวจ capability ซ้ำก่อนเรียก Shared Storage. Mount ownership/session และ project mapping คงอยู่ใน server.
- Upload ใช้ `FormData` และ browser กำหนด multipart boundary เอง. Queue ส่งงานจริงสูงสุด 2 ไฟล์พร้อมกัน, ยกเลิก/ลองใหม่ได้, จำกัดขนาดตาม `maxUploadBytes` และแสดงสถานะโดยไม่สร้างเปอร์เซ็นต์/ความเร็วปลอม.
- Download เริ่มจาก authenticated same-origin Nexora URL และปล่อยให้ browser รับ response stream; ไม่ materialize object ทั้งก้อนเป็น Blob ใน React.
- Rename และ move รักษา logical object ID; copy ต้องคืน ID ใหม่. Move/copy เลือก folder ปลายทางด้วย lazy folder picker และไม่ preload tree ทั้งหมด.
- S2 copy ทำงาน synchronous และรองรับได้สูงสุด 100 objects; operationId ใช้ยืนยันผลตอบรับและไม่มี polling ใน Nexora.
- Session ที่หมดอายุจัดการผ่าน AuthProvider. Stale responses ไม่เปลี่ยน listing ของ storage/folder ปัจจุบัน. Operation ที่ซ้ำบน object เดียวกันถูกป้องกันขณะ request ทำงาน.

## ขอบเขตที่ยังไม่เปิด

Delete, Trash, restore, permanent delete, preview, bulk operations, SMB, persistent Favorites/Share และ Phase 9.4 ไม่ได้เริ่ม. Dashboard, Recent, Favorites, Shared และ Trash ยังใช้ demo state แยกจาก connected mount. Phase 9.2 list/navigation/create-folder behavior ยังคงเดิม.

## Security and contract

Browser ส่งเพียง Nexora `storageId`, logical object ID, logical parent ID, file body และชื่อ object. Browser ไม่ส่งหรือรับ `shared_storage_project_id`, provider reference, bucket/key หรือ Storage credentials. Server resolve mount แบบ owner scoped, derive project ID จาก D1 และตรวจ capability/read-only ก่อน proxy ไป Shared Storage. Upstream download เป็น stream และ upload body ถูกจำกัด/ส่งต่อผ่าน server contract. ไม่มี production credentials ใน tests หรือ fixtures.

## Production Copy incident trace

Production result supplied by the user: upload/download/rename/move pass; Copy returns safe `PROVIDER_UNAVAILABLE`. The redacted log sequence was `stage=mount-resolved`, `stage=capability-check`, bindings present, `stage=request`, `stage=upstream-response status=502`, `result=upstream-http-error status=502`, `result=provider-error`. This proves mount resolution/capability succeeded and the Nexora request received an upstream HTTP 502; it rules out Nexora fetch exception, timeout, JSON parsing, and redirect handling in that attempt. The existing `provider-error` label is based on normalized HTTP status/body code and does not prove the upstream body was generated by S2.

Static request path:

1. File Browser `copyObject` → `copyStorageObject` sends same-origin `POST /api/storage/v1/storages/:storageId/objects/:objectId/copy` with JSON `{parentId}`.
2. Pages API authenticates session, applies same-origin checks, resolves active owner-scoped D1 mount, checks writable state and Shared Storage `copy` capability.
3. Nexora derives `shared_storage_project_id` from that mount and constructs `POST /v3/projects/:projectId/objects/:objectId/copy`. It uses the shared server-side client, configured Access/Bearer headers, timeout and `redirect: 'manual'`. No frontend project identifier or headers are forwarded.
4. Shared Storage S2 route calls `manager.copy`; on file trees the Garage provider performs source Get, target Put, target Head, target Get/checksum, then S2 commits metadata/new object IDs. The successful response is HTTP 201 with `{success:true,object,operationId}`.

The previous Nexora redirect handler followed trusted redirects only for capabilities GET. Copy POST did not use `redirect: 'error'` and did use the same secure fetch helper, but it stopped on a 307/308 response. Source now follows only same-origin 307/308 for Copy POST while preserving method/body; it blocks 301/302/303 and cross-origin, malformed, credentialed, or excessive redirects. This is a proven source-level gap and a safe minimal fix. The supplied production error did not include the new trace, so it is not proven that production Copy received a redirect.

Copy diagnostics record only binding presence, stage, HTTP status, allowlisted error code, redirect classification, JSON/non-JSON body class and result. They do not record storage/project/object IDs, URL, body text, headers, credentials or provider references. A follow-up source change logs only allowlisted upstream error code and body class so the next deployment can distinguish an S2 `PROVIDER_UNAVAILABLE` response from an unrecognized gateway 502. If the body confirms S2 `PROVIDER_UNAVAILABLE`, the S2 source maps unknown Garage errors in the copy pipeline to that code; it still cannot identify source Get, target Put, verification Head or target Get. Do not claim a provider substage without Shared Storage-side evidence.

S2 source/error contract inspected: missing source/destination maps to `NOT_FOUND`; duplicate name to `NAME_CONFLICT`; >100 objects to `OPERATION_TOO_LARGE`; byte verification mismatch to `TRANSFER_INCOMPLETE`; unexpected Garage request errors normalize to `PROVIDER_UNAVAILABLE`; SQLite metadata failures map to `INTERNAL_ERROR` except unique conflicts. The full S2 test suite passed 27/27 and its file-manager tests exercise successful folder-tree copy, source retention, new logical IDs, destination, bytes and provider failures. Nexora tests cover copy URL/method/body/project/headers, same-origin 307/308, cross-origin blocking, operation error mapping (400/404/409/413), provider HTTP error, transport error, timeout, invalid response, and redacted diagnostics.

1. Confirm `GET /api/storage/v1/storages/:storageId/capabilities` returns 200 and includes expected capability flags. Browser must not receive provider project IDs or credentials.

4. Rename it; verify content remains and logical ID is unchanged. Move it into a test folder; verify the same ID appears only at the destination.
5. Copy it into another test folder; verify the copy has a new logical ID and source remains.

7. Verify duplicate-name, missing source/destination, oversized upload/copy, network failure, cancellation/retry and expired-session messages remain safe and do not expose upstream response bodies or credentials.

The key line should be `result=upstream-http-error status=... body=json|other code=<allowlisted-code|unknown>`.
